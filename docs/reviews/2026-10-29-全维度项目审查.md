- [src/core/guard.ts:72-76](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/guard.ts#L72)

**问题**：批 B3 的承诺是"同参数连续 3 次失败拒绝执行"，目标域是 write/destructive/process 类 action（`tool-circuit-breaker.ts:9` 边界注释明言）。但两条集成链路使该承诺在默认配置下完全落空：

**F1：真实执行经 confirm_and_execute 两轮往返，绕开熔断**。`requiresConfirmation`（guard.ts:74-76）对一切 risk≠read 的 action 返回 true → scene.commit / execute_gdscript / game_write 等**全部**走"第一轮返回 requires_confirmation（非错误，不计失败）→ 第二轮 confirm_and_execute"流程。真实执行发生在 `_confirmExecute` 内（ToolDispatcher.ts:500/545），其外层 middleware ctx.toolName = `confirm_and_execute`，`getActionRisk('confirm_and_execute', …)` 对 inline 工具恒返 undefined → `isBreakable` 恒 false（tool-circuit-breaker.ts:108-118）。**熔断能统计到的失败只有首轮前置校验错误（INVALID_PARAMS 等），而它声明的目标域（写类工具真实执行失败）一条都记录不到**。

**F2：project_path 注入使指纹在 before/after 间漂移**。`executeToolCall` 在 middleware.before 之后、after 之前原地注入 `args.project_path`（ToolDispatcher.ts:338-348，且与 ctx.args 同引用——:306-308 注释确认 ctx.args 是可变载体）。before 键 = 不含 project_path 的指纹；after 键 = 含 project_path 的指纹。失败计数落在 after 键，开路检查查 before 键——**客户端省略 project_path（默认 GODOT_PROJECT_PATH 单项目场景，最常见形态）时开路状态永远查不到，TOOL_CIRCUIT_OPEN 永不返回**。F1 与 F2 叠加：默认配置下熔断完全惰性。

**测试盲区**：`test/core/tool-circuit-breaker.test.ts`（178 行）只测 middleware 孤体（注入 mock risk 表），无 dispatcher 集成测试、无确认流测试、无 project_path 省略路径测试——批 B 审查"B3 熔断正确性——通过"的结论建立在孤体正确性上，集成面从未被测。

**修复建议**
- 在 `_confirmExecute` 执行前后接熔断钩子（按 `pending.toolName`/`pending.args` 计键），或把熔断下沉到 `_dispatchEditorOrHeadless` 内部。
- keyOf 前剔除注入类字段（project_path 等），或 middleware 在注入前快照指纹。
- 补 dispatcher 级集成测试：确认流中同参 3 败→第 4 次拒绝；客户端省略 project_path 时熔断仍生效。

## 7. 分维度结论

### 7.1 架构与核心入口
- 批 B3 熔断遵守仓库约束：工厂+闭包注入、无新增模块级 setter、core 无 tools 依赖；middleware 插位（healthSample→telemetry→circuitBreaker→audit→rate-limit→elicitation）与顺序锁注释一致。
- 场景工具拆分（scene-commit-tool / scene-commit / commit-restore）边界清晰，dry_run 探测脚本与 handler 分流设计合理。
- **但 middleware 孤体正确 ≠ 集成正确**：F1（confirm 两轮通道绕过）与 F2（注入序致指纹漂移）都是只有 dispatcher 级视角才能看到的缺陷——批 B 审查只测了孤体。

### 7.2 安全

### C-1（Critical）动态工具的破坏性动画 action 绕过确认令牌

**位置**
- [src/core/dynamic-risk-map.ts:48](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/dynamic-risk-map.ts#L48)
- [src/core/ToolDispatcher.ts:397](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/ToolDispatcher.ts#L397)
- [src/core/guard.ts:64](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/guard.ts#L64)
- [src/tools/animation/animation-track.ts:277](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/animation/animation-track.ts#L277)
- [src/core/editor-method-map.ts:85](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/editor-method-map.ts#L85)
- [src/core/EditorToolExecutor.ts:111](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/EditorToolExecutor.ts#L111)
- [addons/godot_mcp_server/commands/animation_commands.gd:26](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/addons/godot_mcp_server/commands/animation_commands.gd#L26)

**问题**

`METHOD_TO_TOOL` 把动态工具名映射为固定的静态 action，而不是按调用参数中的真实 action 解析：

```ts
// dynamic-risk-map.ts:48-49
animation_track:     { tool: 'animation_track', action: 'add_track' },
animation_keyframe:  { tool: 'animation_track', action: 'add_keyframe' },
```

ToolDispatcher 在确认判定时用映射值**覆盖**了真实参数：

```ts
// ToolDispatcher.ts:400-401
const guardArgs = (legacyMap ?? dynMap) ? { ...args, action: legacyMap?.action ?? dynMap?.action } : args;
const confirmRequired = ... || requiresConfirmation(guardName, guardArgs);
```

而两者的真实风险不同：

```ts
// animation-track.ts:278-283
add_track: 'read',
remove_track: 'destructive',
add_keyframe: 'read',
remove_keyframe: 'destructive',
update_keyframe: 'destructive',
```

GD 端动作名是短名 `add/remove/update`（`animation_commands.gd:19,32`）；`remove` 删除轨道/关键帧，`update` 修改关键帧值。

**影响链路**

1. AI 调用动态工具 `animation_keyframe`，参数 `action: "remove"`（或 `"update"`）。
2. 门禁按 `animation_track + add_keyframe` 判定风险 = `read`，不要求确认令牌。
3. `EditorToolExecutor` 对动态名没有静态映射（`resolveEditorMethod` 未命中），按原名 `animation_keyframe` 与**原参数**转发（`EditorToolExecutor.ts:111-113`）。
4. GD 端执行删除/更新，无任何确认。

`animation_track` 的 `action: "remove"` 同样绕过。这不是单个工具的偶发问题，而是“一个动态 method 内含多个 action，静态映射只登记其中一个”的结构性缺陷；今后任何新增多 action 的 GD method 都会复现。仓库内已有测试未覆盖“dynamic + 非默认 action”的组合。

**修复建议**

- 确认/action-gate 应基于 `(method, actualAction)` 解析风险；`METHOD_TO_TOOL` 至少改为 `Record<method, Record<action, {tool, action}>>`。
- 或对动态工具统一做 fail-closed：无法把真实 action 映射到已知静态 action 时一律要求确认。
- 增加回归测试：`animation_keyframe{action:"remove"}` 与 `animation_track{action:"remove"}` 必须返回 `requires_confirmation: true`。

### B-1（Blocking）Docker 镜像启动即 FATAL 退出

**位置**
- [Dockerfile:13](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/Dockerfile#L13)
- [src/index.ts:46](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/index.ts#L46)

**问题**

镜像设置：

```dockerfile
ENV GODOT_MCP_UNRESTRICTED=true
```

而启动序列在非开发模式下对任何危险环境变量的**存在**（`!== undefined`）直接退出：

```ts
if (!isDev) {
  for (const flag of dangerousBypassFlags) {
    if (process.env[flag] !== undefined) {
      console.error(`[FATAL] ${flag} is set ... Exiting.`);
      process.exit(1);
    }
  }
}
```

`isDev` 需要 `NODE_ENV=development` 或 `GODOT_MCP_ALLOW_UNSAFE=true`，Dockerfile 均未设置。

**实测**：`GODOT_MCP_UNRESTRICTED=true node build/index.js </dev/null` → `[FATAL] GODOT_MCP_UNRESTRICTED is set but NODE_ENV is not "development".`，exit 1。容器/Glama 等基于 Dockerfile 的分发入口不可用。

**修复建议**

- 删除该 `ENV`；如确需容器内不受限，另建显式的 dev 镜像并同时设 `NODE_ENV=development`，不要在默认运行镜像中开启。
- 增加 Docker smoke CI（构建 + `docker run` + `doctor`/stdio 握手）。

### H-1 截图以“文件存在”判定成功，复用陈旧截图

**位置**：[src/screenshot.ts:185](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/screenshot.ts#L185)、[src/tools/screenshot.ts:121](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/screenshot.ts#L121)

**问题**：`captureScreenshot` 在校验 Godot 退出码之前，仅凭 `existsSync(outputPath)` 返回成功：

```ts
const result1 = await runScreenshot(...);
if (existsSync(outputPath)) {          // 可能是上一次的旧图
  return { success: true, imagePath: outputPath, ... };
}
```

默认输出固定为 `<project>/screenshot.png`，同一项目第二次截图会命中旧文件。即使本次 Godot 崩溃、场景加载失败或超时，也会返回 `success: true` 和旧图片；重试分支（`:206`、`:228`）同样如此。

**影响**：视觉验证、`verify_delivery`、交付证据链可被旧图“假通过”。这是验证完整性问题，不只是便利性问题。

**修复建议**：运行前删除目标文件，或记录起始时间/文件指纹并要求“mtime ≥ 启动时间且大小 > 0”。建议优先 `unlinkSync`（对用户指定 `output_path` 亦然），并添加“Godot 失败但旧文件存在”回归测试。

### H-2 frame_sequence 归档链路必被沙箱拦截，且错误不进入 acceptance

**位置**：[src/tools/workflow.ts:474](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/workflow.ts#L474)、[src/tools/frame-verify/proof-bundle.ts:21](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/frame-verify/proof-bundle.ts#L21)、[src/core/sandbox-scanner.ts:55](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/sandbox-scanner.ts#L55)、[src/gdscript-executor.ts:678](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/gdscript-executor.ts#L678)

**问题**：frame_sequence 生成服务端 GDScript 写绝对路径：

```ts
const copyScript = `extends SceneTree
func _initialize():
	var img := Image.load_from_file("${tmpPath}")
	var f := FileAccess.open("${run.dir}/${frameName}", FileAccess.WRITE)
	...
`;
const copyResult = await executeGdscript({ ... });
```

- `run.dir` 是绝对路径（[proof-bundle.ts:13,21](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/frame-verify/proof-bundle.ts#L13)）。
- 调用的是普通 `executeGdscript`，默认开启沙箱；扫描器对任何 `FileAccess.open(..., FileAccess.WRITE)` 都报 `File write access`，与路径是否在项目内无关（`sandbox-scanner.ts:55`）。
- 因此每帧都会返回 `compile_error: "Sandbox violation: ..."`，`captureError` 被写入 `result.frame_sequence.error`，但 acceptance 的通过条件只看断言列表：

```ts
result.acceptance = { passed: assertionResults.every(r => r.passed), results: assertionResults };
```

帧捕获失败、甚至完全没捕获到帧，`acceptance.passed` 仍可为 `true`。此外，Win 路径反斜杠未转义，即使关闭沙箱也可能出现非法转义。

**修复建议**

- 该代码完全是服务端生成，只有受控路径参与拼接：改用 `executeGdscriptTrusted`，并对路径做 GDScript 字符串转义（统一正斜杠 + 转义 `"`/`\`）。
- 或调整流程：bridge 截到 `user://` 后由 TS 侧经 Godot 一次性输出 base64（仍走受控脚本）；避免在默认沙箱通道写绝对路径。
- `acceptance.passed` 必须纳入 `frame_sequence.error`、帧数与 `count` 的一致性。

### H-3 验收断言可“空代码通过”，ASSERT 协议与实际判定脱节

**位置**：[src/tools/workflow.ts:667](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/workflow.ts#L667)、[src/tools/shared/assertions.ts:24](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/shared/assertions.ts#L24)

**问题**

workflow 的通过条件：

```ts
const actual = String(assertResult.outputs.find(e => e.key.startsWith('assert_') || e.key === 'assert_result')?.value ?? '');
const passed = a.expect ? actual === a.expect : true;
```

- 未提供 `expect` 时，只要断言脚本编译并运行成功（即使用户代码是空的）就 `passed: true`。
- `expect` 为空字符串时同样走“必过”分支（falsy）。
- wrapper 实际打印的是 `ASSERT PASS/FAIL`（`assertions.ts:24-39`），但 workflow 完全不解析该输出；两套协议各说各话。
- wrapper 自身的 PASS 条件是 `assert_result != ""`，即使值为字符串 `"false"` 也打印 PASS，语义错误。

**影响**：`dev_loop` 的 acceptance 可作为交付门禁，但“没有断言代码”或“忘记输出 assert_result”都可能被记为通过；反过来，提供 `expect` 但未输出 `assert_result` 会稳定假红。现有 E2E `dev_loop acceptance gdscript 断言真链路` 能通过，恰好依赖了会输出 `assert_result` 的用例，未覆盖空代码/无 expect 场景。

**修复建议**

- 让 wrapper 输出结构化判定（如 `_mcp_output("__assert_pass", "true"/"false")`），workflow 读取该字段；`ASSERT PASS/FAIL` 仅作人类可读日志。
- 强制断言必须产出 `assert_result`（或显式的布尔字段），否则判失败。
- `expect` 用 `!== undefined` 判断；补充空代码、恒真、恒假、字符串 "false" 四类回归测试。

### H-4 非交互执行 `install` 以 0 退出但未安装

**位置**：[src/cli/confirm.ts:7](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/cli/confirm.ts#L7)、[src/cli/godot-installer.ts:207](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/cli/godot-installer.ts#L207)、[src/index.ts:286](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/index.ts#L286)

**问题**：`confirmYesNo` 在非 TTY 下直接 `return false`；installer 将其转成 `InternalError('install cancelled by user')`；入口把 `/cancelled by user/` 统一映射为 `exitCode = 0`。`install` 没有 `--yes`。

结果：CI/管道/容器里执行 `godot-mcp-enhanced install`，不下载、不安装、提示“已取消”，但退出码 0，自动化会判定成功。对比之下 `uninstall` 明确实现了“非交互且无 `--yes` → exit 2”，install 缺少同等处理。

**修复建议**：区分“用户主动取消（TTY）”与“非交互无法确认”；后者 exit 非 0 并给出 `--yes` 指引；为 install 增加 `--yes`。

### H-6 snippet 模式将字符串/注释中的 `root` 一并重命名

**位置**：[src/gdscript-executor.ts:409](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/gdscript-executor.ts#L409)

**问题**：为避免用户 `var root` 与 `SceneTree.root` 冲突，wrapSnippet 对整行做正则替换：

```ts
const refPattern = new RegExp(`(?<![_.\\w])\\b${reserved}\\b(?!\\w)`, 'g');
// 应用于 declarationLines 与 statementLines 的所有行
```

该正则不区分代码、字符串和注释。实测语义等价示例：

- `print("root")` → `print("_mcp_user_root")`
- `get_node("/root/Main")` → `get_node("/_mcp_user_root/Main")`
- 注释中的 `root` 同样被改写

**影响**：snippet 模式静默改变用户输出与节点路径，可能造成运行错误或错误断言；对 `execute_gdscript` 这种高频入口影响面大。

**修复建议**：只重命名标识符 token；至少跳过字符串字面量与注释（可复用仓库已有 tokenizer），或改用不冲突的包装策略（例如仅当声明行确为 `var root` 时才做局部重写）。

### M-2 POSIX 超时后无法升级到 SIGKILL

**位置**：[src/core/process-state.ts:24](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/process-state.ts#L24)、[src/core/process-state.ts:81](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/core/process-state.ts#L81)

`forceKillTree` 首行 `if (proc.killed) return;`。`killProcess` 先 SIGTERM（Node 将 `proc.killed` 置 true），5 秒兜底再次调用 `forceKillTree` 时直接返回，永远不会 SIGKILL。Godot 忽略/阻塞 SIGTERM 时会留下孤儿进程，而 Promise 已 resolve，上层认为清理完成。Windows 的 `taskkill /F` 不受影响。

**建议**：兜底路径不检查 `proc.killed`，直接 `SIGKILL`（POSIX）；并等待真实 `exit/close` 再 resolve。

### M-3 `close()` 无并发/重入保护，自重启与请求处理重叠

**位置**：[src/GodotServer.ts:860](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/GodotServer.ts#L860)、[src/GodotServer.ts:698](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/GodotServer.ts#L698)

`close()` 只用一个局部 `serverClosed` 标志防止 `server.close()` 重复调用；清理链其余步骤（in-flight、DAP、editor manager、进程 kill、模块 setter）可被并发执行两遍。`onSelfRestart` 在 `close()` 完成后立刻 `process.exit(0)`，期间 stdio 仍可能接收新请求。

**建议**：实例级 `_closing` Promise 复用；入口在 closing 后拒绝新调用；重启路径先停止接收请求再退出。

### M-4 `project_replace` 在 dry-run 下删除用户 `*.bak` 文件

**位置**：[src/tools/script/project-replace.ts:27](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/script/project-replace.ts#L27)、[src/tools/script/project-replace.ts:36](file:///D:/GitHub/godot-mcp-series/godot-mcp-enhanced/src/tools/script/project-replace.ts#L36)

残留清理在解析 `dryRun` 之后、但在 `if (!dryRun)` 写入保护之前无条件执行：删除项目根与一级子目录下所有 `*.bak` / `*.mcp-tmp`。用户自己的 `save.gd.bak`、根目录备份文件会在“仅预览”调用中被删除。清理只扫一级目录，而写入产生的是 `*.tmp`（不是 `.mcp-tmp`），与注释所称“中断残留”并不一致。

**建议**：dry-run 绝不产生写/删副作用；只清理本次命名空间内、可证明由工具创建的临时文件，或把清理延后到真实写入路径。

### M-5 CLI `setup` / `uninstall` 吞掉失败仍以 0 退出

### M-8 JSON 客户端反配置会丢失 JSONC 注释且无备份

## 6. 分维度结论

### 6.1 架构与核心入口

- 三层职责分离清晰；工具合并 + action 路由使 272 个 action 保持 46 个顶层工具，规模控制合理。
- 单入口 `ToolDispatcher` 把 profile / action-gate / 确认令牌 / 路径白名单 / 审计串成链，结构正确。
- 缺陷集中在“动态工具”这一后加通道：静态风险表与运行时 action 不是同一维度（C-1），说明门禁抽象尚未完全覆盖动态命名空间。
- `close()` 的清理链设计（safeStep）很好，但缺少整体幂等封装（M-3）。

### 6.2 安全

- 路径白名单、realpath 校验、GDScript 沙箱、确认令牌、审计、Web GUI token/CSP、多实例 registry 均有实质实现，且注释中保留了威胁模型与残余风险说明，整体成熟。
- 沙箱定位被明确为“防误操作而非信任边界”，与 `GODOT_MCP_UNRESTRICTED` 双开关设计一致。
- 主要问题不是“沙箱逃逸”，而是**授权层语义错配**（C-1）与**发布配置错误**（B-1）。
- editor/bridge 保留 legacy 明文认证降级，属于已披露的本机威胁模型取舍；高安全部署应强制 `GODOT_MCP_EDITOR_REQUIRE_CR_AUTH=true` / bridge 对应开关。

### 6.3 正确性与验证可信度

- 三个“验证结果不可信”问题（H-1 截图、H-3 断言、H-2 帧捕获）比普通功能 bug 更严重，因为它们直接削弱项目主打的“read / write / run / verify”闭环。
- snippet 的 `root` 重命名（H-6）与 autoload 实例不入树（M-1）说明动态生成代码的边界处理仍偏正则化，建议长期引入词法级处理。
- 输出截断、proof 清理、`waitMs(0)` 等属于可观测性/资源卫生问题，不影响主路径但会干扰诊断。

### 6.4 并发与生命周期

- editor 工具串行链、长操作心跳暂停、DAP 清理、in-flight 记录等设计考虑周全。
- 仍存在 POSIX 强杀不升级（M-2）、close 重入（M-3）、in-flight/audit 读改写竞态（L-13/L-14）、pending 请求悬挂（L-9）等问题；均为低频但难以诊断的可靠性缺陷。

### 6.5 CLI 与供应链

- 子命令体系、JSONC 备份、SHA512 校验、zip 安全解压（除目录条目）、审计留痕均较完整。
- 退出码语义是主要短板：install（H-4）、setup/uninstall（M-5）在失败或未执行时返回 0，直接破坏 CI 可用性。
- npx 路径判定（M-6）会让最常见的试用方式生成不可持久化配置。
- 依赖安装/下载缺少超时（L-17），在弱网/被墙环境会长时间挂起。

### 6.6 文档与发布物

- README 主体信息密度高、口径解释清楚，但英文 README、instructions、`docs/tools` 与实现存在系统性漂移（H-5）。
- 由于 `docs/tools` 随 npm 分发，这不是“仓库内文档小问题”，而是**发布物缺陷**。
- 建议建立“生成物必须可复现”门禁：tool docs、matrix、版本号、README 计数统一由脚本产出并 CI diff。

### 6.7 GDScript 插件与 game bridge（抽查）

- WebSocket 服务端：secret 生成/权限收紧、challenge-response + 恒时比较、按 peer 的失败锁定、握手超时、最大 peer 数、inbound/outbound 缓冲上限均已实现；未认证请求统一拒绝。
- 命令分发：`command_handler.gd` 使用显式 `match` 白名单；bridge 端对 `call_method` 有方法白名单/黑名单与 player 模式限制，禁止 `call/callv/emit_signal/connect` 等间接执行入口。
- 未发现新的 High/Critical；但 C-1 的根因在 TS 授权层，GD 端按设计执行 `remove/update` 是正确行为，修复应在 TS 侧完成。
- **限制**：本轮未运行 Editor/GUI 端到端，也未对 34 个 `.gd` 做逐行完整审计；结论仅覆盖鉴权、分发与高风险 API 白名单。

### 6.8 测试与工程门禁

- 单元测试覆盖面广（503 文件），测试质量门禁（830 ≤ 860）通过；脚本门禁大多有效。
- 真 Godot 集成测试与并行 runner 的相互作用导致全量不稳定（M-7），覆盖率运行也因共享 fixture 冲突出现 4 个失败；覆盖率阈值本轮**未获得可信的通过证据**。
- 缺少针对本轮关键缺陷的测试：动态 action 确认、陈旧截图、空断言、frame_sequence、Docker 启动、非交互 install 退出码。

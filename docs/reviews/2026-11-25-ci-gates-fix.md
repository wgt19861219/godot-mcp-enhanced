**c78fd08c fix(scripts):署名尾行按行剥 + 追踪号收窄为登记键族(首版)**

**2d1fb9dd test(qa):qa-tasks-wire 计时断言拉开与后台套件时长的余量**

- **复现**:40 个忙循环进程压 20 核,12 轮里 1 轮失败(实测 403ms,阈值 150ms)。
- **改法**:模拟后台套件 2000ms、阈值 1000ms。
- **变异检验**:把 `src/tools/qa/index.ts` 的自动异步分流临时改成同步路径(等套件完成再返回),用例仍失败在计时断言上(实测 2036ms);随后 `git checkout` 恢复,确认与 HEAD 一致。
- **复验**:同款负载 20 轮 0 失败。

**b8a8f0a2 test(cli):init.test.ts 清理临时目录带重试**

- **复现过程(含两轮作废的实验)**:
  - 第一轮假设「文件被占用形成删除挂起」:libuv 默认共享模式的文件句柄被其它线程持有,三种选项都 1~3ms 删除成功——不是成因。
  - 第二轮假设「目录句柄被占用」:用了 `fs.opendirSync`,而它在 Windows 上是 `FindFirstFile` 搜索句柄,并不持有目录句柄,结论无效。
  - 第三轮占用者矩阵(前两轮的缺陷已纠正:用 `CreateFileW` 真正打开目录句柄,并校验占用者确实打开成功):不含删除共享的文件/目录句柄、或外部进程 cwd 在目录内 → 默认报 `EPERM`;含删除共享的目录句柄 → 1~2ms 直接成功。仍未造出 `ENOTEMPTY`。
  - 最终造出 `ENOTEMPTY` 的是「删除进行时另有线程往目录里写新文件」:默认选项稳定报 `ENOTEMPTY(rm)`(3/3,约 105ms)。
- **结论边界**:`ENOTEMPTY` 的来向(删除时目录里仍有或又出现目录项)与重试的有效性(干扰一停即删成功,约 0.9s;`EPERM` 各形态同样被重试化解)是证实的;真实运行里是哪个外部进程造成残留,**未复现,不下结论**。
- **改法**:`maxRetries: 5, retryDelay: 100`。同款负载下 `init.test.ts` 15 轮 0 失败(该负载本就复现不出这条,只作冒烟)。

**064a2458 fix(scripts):白名单按实测词形补全**

- **问题**(第二轮复审 I-1):首版白名单只认 `SEC-数字`。全史提交里 SEC 族出现 37 次,其中带类别前缀的 `C-SEC-01` / `I-SEC-08` 与阶段复合的 `SEC-P2-1` 合计 28 次——这条门禁为安全修复而设,对多数写法反而看不见。CMP / Pn-x 的字母后缀子项(`CMP-9B` / `P2-1R`)与 GHSA 短写(`GHSA-jm63`)同样抽不到。原正则与中间版本都能抽到它们,属回退。
- **成因**:控制器之前按「首个连字符前的前缀」统计词族,把 `C-SEC-01` 并进了 `C`、`SEC-P2-1` 并进了 `SEC`,没有逐词形核对。
- **改法**:按全史提交与 CHANGELOG 的实际词形重定——
  `(?<![A-Za-z0-9-])(?:(?:[A-Z]-)?SEC-(?:P\d+-)?\d+|CMP-\d+[A-Za-z]?|SEP-\d+|P\d+-\d+[A-Za-z]?|CVE-\d{4}-\d{4,}|GHSA-[0-9a-z]{4}(?:-[0-9a-z]{4}){0,2})(?![A-Za-z0-9])`
- **验证**:
  - TDD:先补「登记键词形未登记须阻断」表 4 例,对首版脚本全红(`4 failed / 14 passed`);改后 `18 passed`。
  - 词形抽样 41 例全部符合预期:17 种应命中的登记键全中,24 种不该命中的全不中。
  - 全史 feat/fix 提交 1555 条里抽出追踪号的 110 条、99 个不同追踪号,词形全部落在登记键族内,无新增噪音。
  - 真实仓库登记后 18 个均已登记。

**同笔补的用例盲点(第二轮复审 M-3 / M-4 / M-5)**

- 两条署名尾行用例改成非空过。首版白名单一上,`GLM-5.4` 本就不受检,把换行拼接改回空格拼接它们照样绿。现在尾行里放白名单形态的追踪号,变异检验实测:基线 4 红 → 撤销换行拼接 5 红(「按行拼接」一例)→ 撤销尾行剥离 6 红(两条尾行用例)。

## 七、工程教训

1. **修「误报类门禁」要把最常见的输入形态各补一例。** 尾行剥离只测了「正文有段落再署名」,漏了 `-m 主题 -m 尾行` 这种最短的形态;修一处误报时,同一处换个拼写往往还藏着一处(I-1、I-2 都是 `d3f0b705` 的残留)。
2. **收窄正则前先量数据,而且要逐词形核对。** 按「首个连字符前的前缀」统计,把 `C-SEC-01` 并进了 `C`、`SEC-P2-1` 并进了 `SEC`,结果首版白名单漏掉了 SEC 族的多数写法。统计词族要按完整词形,不能只看前缀。
3. **改了一条被依赖的判定规则,要回头检查既有用例是否变成空过。** 白名单一上,两条署名尾行用例就不再钉住换行拼接与尾行剥离——它们当时是红的,只说明「在当时那版脚本上」有区分力。用变异检验(把修复撤销,看用例是否变红)确认,比看它绿着可靠。
4. **没有导入方的脚本不要加入口判断。** 「仅直接执行时才跑」对它只有风险:路径含 junction 时静默空转。
5. **本地全量的 flaky 是按「族」出现的**:零余量计时断言、不带重试的目录清理、全局端口探测。修一条再跑只会换下一条;先按同形态 grep 排查整族,再决定修到什么程度、要不要继续跑。
6. **设计复现实验前先确认「占用」真的成立。** 两轮无效实验都栽在没校验占用者状态(`fs.opendirSync` 不占目录、`.NET File.Open` 打不开目录)。
7. **CPU 超订阅负载只是一种代理。** 它只在启动突发的那一轮复现过一条,对全量里的同步 I/O 阻塞与 GC 停顿没有代表性;负载下没复现不等于没有风险,反过来也一样。
8. **本地全量红而单跑绿时,先看并发口径。** CI 是 `--maxWorkers=2`,本地默认按核数。
9. **Node 24 的 `fs.rmSync` 是原生实现**(`binding.rmSync(path, maxRetries, recursive, retryDelay)`),JS 侧看不到重试逻辑;`maxRetries` 按线性退避,`maxRetries: 5 / retryDelay: 100` 合计约 1.5s。
10. **门禁会查修门禁的那笔提交自己。** fix 提交的说明里出现追踪号,它自己也要被登记;固定收尾顺序(最后一笔 fix → 按哈希登记 → 在最终提交上重跑 → 不再变基),今天三次都靠这个顺序过。

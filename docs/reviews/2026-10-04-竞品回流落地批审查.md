## Blocking Issues 与处置

### B-1(置信 85)✅ 已修复
**问题**:`call_method await_completion=true` 走 GD `__DEFERRED__` 延迟通道(`mcp_bridge.gd` 协程推送响应,不入幂等缓存),但 TS 对 `game_write` 全量生成幂等键并输出"传同一 request_id——不会重复执行"的超时指引。五步证据链:`game-bridge.ts` 无条件生成 idemKey → GD 返回 `{"__deferred__": "call_method_async"}` → 延迟通道在 `_cache_idempotent_response` 之前 return → 长协程超时 → agent 按指引重试同 requestId → 缓存 miss → **重新执行副作用**。矛盾三重佐证:附二"写类高危命令全在同步路径"对该变体不成立;await 恰是超时概率最高的写命令形态;新增用例只测了 set_node_property 形态。

**修复**(TS 侧方案):`src/tools/game-bridge.ts` `isAwaitCallMethod = method === 'call_method' && params.await_completion === true` 排除在幂等键之外,超时走"必须先核实"降级文案;GD 常量区注释与方案附二同步修正措辞;补回归用例两条(await 变体无 requestId / 同步 call_method 对照组仍发)+ GD 源码契约测试(`test/bridge-idempotency-contract.test.ts` 5 用例,含"延迟 return 先于缓存写入"的结构锁——B-1 类缝隙的机械防线)。

## 值得进 memory 的工程教训(审查者提炼)

1. 幂等层的**保护面必须与错误指引的承诺面逐命令变体对齐**——TS 对 game_write 全量发幂等键而 GD 延迟通道不入缓存,`call_method await_completion=true` 落在缝里,"传同一 request_id 不会重复执行"成了假承诺。
2. mock 到协议边界的单测会把"两端各自正确、拼起来错"的矛盾留在盲区——跨端契约类改动至少要枚举命令的全部延迟/同步形态各一条用例。
3. 探针实证修正实现后要回扫文档与注释里的旧 API 名,否则教训本身会以错误形态被复制。

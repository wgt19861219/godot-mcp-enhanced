# 可维护性质量评估（2026-09-20）

> **评估类型**：横向质量评估（非 feature 落地审查）
> **评估维度**：模块化 / 可复用性 / 易分析性 / 易修改性 / 易测试性
> **评估方式**：全部结论基于实测命令（见附录），无主观推测数字；所有计数口径在文中标注
> **评估基线**：master @ 74111e23，package.json 0.33.8

---

## 总体判定

**总体 4.0 / 5.0（良好偏优）**。分层维度：模块化 4.5、可复用性 4.0、易分析性 3.5、易修改性 4.0、易测试性 4.0。

一句话结论：**结构纪律与机械门禁是本项目的可维护性核心资产**（零循环依赖、eslint 分层门禁、组合根集中、strict TS 零 any、473 测试文件三重验证链），主要负债集中在**三个核心链路大文件**（gdscript-executor 1579 行 / script.ts 1236 行 / ToolDispatcher 1178 行，其中 executeToolCall 单方法约 440 行）、**模块级 setter 单例群**（实测 26 个，close() 手动对称清理靠纪律）与**6 个 ≥400 行无测试引用文件**。

## 维度一：模块化 —— 4.5 / 5.0

**优势（均有机械门禁背书，非口头约定）**：

1. **零循环依赖（实测）**。263 文件全图 DFS 无环。这在 105 文件的 tools 目录 + 60 文件 core 并存的规模下不常见。
2. **分层有 eslint 强制**：`eslint.config.js:30-35` 用 `no-restricted-imports` 禁止 `src/core/**` import `../tools/`、`../web-gui/`，违规即 CI 失败。组合根 `src/module-loader.ts`（294 行）集中全部工具 import，且 `ALL_MODULES` 数组由 `scripts/generate-all-modules.mjs` 自动生成（注释明示"勿手动编辑"），消除人工清单漂移。
3. **三层域架构有明文定义**（AGENTS.md「域×通道矩阵」）：headless/editor/bridge 三域四通道，新增工具必须先声明归属。2026-09-12 D2 定规后表述已覆盖 DAP 免登记通道的例外。
4. **子系统边界总体干净**：
   - `scoring/` 仅依赖 `src/types.ts` + `core/godot-spawn.js`，可独立演进；
   - `cli/clients/` 15 个适配器全部 29-177 行小文件，共用 json-config/json-adapter 基建，新增客户端是填空题；
   - `tscn/` 5 文件自成一体。
5. **目录分组规则明文化**：≥2 源文件建同名目录、单文件平铺（AGENTS.md「src 目录分组规则」），判定依据是职责可分性而非行数——这避免了"为拆而拆"。

**弱点**：

- **W1（低）**：`src/tscn/tscn-editor-add.ts:17` import `../tools/scene/helpers.js` 的 `BLOCKED_PROPS`——底层解析子系统反向依赖上层工具目录，属性黑名单应下沉到 core/shared。
- **W2（低）**：`src/dashboard/launcher.ts:8` import `../web-gui/server.js` 的 `isWebGuiActive`——两个定位为平行的监控面（TUI 独立进程 vs server 内嵌 HTTP）存在单向耦合，dashboard 的"独立只读"边界被打了孔。
- **W3（中，已知挂账）**：26 个模块级 setter 单例（bridge-client/elicit/process-state/progress/logger/tool-registry 等 11 文件）。AGENTS.md 已定规"禁止新增 + 存量清算为长期项"，`GodotServer.close()`（760-900+ 行）逐一手动对称置 null。风险受控但每次新增全局态都要靠纪律补清理。

## 维度二：可复用性 —— 4.0 / 5.0

**优势**：

1. **样板收敛在持续发生且留痕**：`src/tools/shared/ops-runner.ts`（2026-09-18 建）把 10 个 ops 工具（audio/animtree/ik/physics/particles/node-3d/navigation/signal/tilemap/uid）的"execute→parse→warn"尾部链收敛为单一 `runOpsScript`，差异点（errorMapper、trusted 通道、持久化警告）参数化保留在调用方——这是教科书式的"统一流程 + 注入差异"。
2. **双层共享库分工清楚**：`core/shared/`（errors、gdscript-templates，面向全仓）+ `tools/shared/`（assertions、file-guard、ops-runner、value-serializer 等，面向工具层）。`value-serializer` 被 7 个文件引用。
3. **向后兼容桶 `src/tools/shared.ts`** 让 20+ 存量 import 位点平滑迁移到新路径。
4. **测试基建复用**：`test/helpers/`（fixtures / mock-results / path-isolation / tool-context）被 24 个测试文件引用，mock 与路径隔离不用每个测试重造。
5. **跨文件重复极少**：12 行窗口级重复全仓仅 7 处，且全部是 ui/、animation/ 同族工具生成 GDScript 的模式性相似（如 `animPreamble` + `trackRangeGuard` 前导），不是跨子系统复制粘贴。

**弱点**：

- **W4（低）**：ui-create / ui-layout / ui-draw / ui-theme 之间的 GDScript 生成前导（animPreamble/trackRangeGuard 组合）仍有 2-4 处窗口重复，可仿照 ops-runner 再收敛一层到 `tools/animation/shared`。
- **W5（中）**：`src/helpers.ts` 废弃桶——文件头标注 `@deprecated since v0.19.0`、`TODO: v0.20.0 remove barrel`，当前版本 **0.33.8**，废弃计划拖了 14+ 个小版本，仍有 **45 个 import 位点**未迁移。这不是功能问题，但"计划内清理"长期不兑现会侵蚀后续类似承诺的可信度（对照：CHANGELOG 里 [Unreleased] 流程是严格执行的）。

## 维度三：易分析性 —— 3.5 / 5.0（五维中最弱）

**优势**：

1. **注释纪律好**：大文件普遍有 `───` section 分段（gdscript-executor.ts 有 7 个 section），`module-loader.ts` 每个 import 行标注工具用途与引入批次（如 `// P9 (2026-09-12): debug 组 DAP 断点调试`），历史合并轨迹（"batch-tools → merged into workflow (v0.18.0)"）也留痕。
2. **工具面对账机器化**：capability-matrix 由 `npm run build-matrix` 从源码生成，防止文档与工具清单漂移。
3. **决策记录制度化**：`docs/reviews/` 审查文档持续产出（最近到 2026-09-20）、AGENTS.md 记录定规日期与出处（如"2026-08-21 架构审查定规"）、CHANGELOG 2056 行、README 877 行。新人可以从文字记录重建"为什么"。

**弱点**：

- **W6（高，本次评估最大扣分项）**：核心执行链路文件过大，理解成本集中在少数单点：
  - `src/gdscript-executor.ts` 1579 行——沙箱扫描 + autoload 修复 + 取证审计 + 执行通道混在一文件（虽然 section 分段缓解，33 个函数职责仍跨 4 个主题）；
  - `src/tools/script.ts` 1236 行；
  - `src/core/ToolDispatcher.ts` 1178 行，其中 `executeToolCall`（316-518 行）**单方法约 200 行**且 `buildMiddleware`（520-688 行）内联约 168 行中间件工厂（audit 一段约 80 行）——方法/工厂粒度的多职责混杂是全仓最难读的单点。
  - **口径修正（2026-09-20 当日复核）**：本报告初版误将 executeToolCall 记为"316-757 行约 440 行"——316-757 区间实际还包含 buildMiddleware / setConnectionMode / normalizeArgs 等多个方法；初版以方法起始行粗测未核实结束行，教训记 memory。
  - AGENTS.md 的"大文件单职责不拆"规则对 dispatcher 这种多职责方法粒度没有约束（规则只到文件粒度）。
- **W7（低）**：`src/web-gui/html.ts` 1068 行内联 HTML/JS——前端资源嵌在 TS 字符串里，无法用前端工具链（格式化/lint/语法检查）分析。

## 维度四：易修改性 —— 4.0 / 5.0

**优势**：

1. **新增工具路径是明文流水线**：写模块 → module-loader 加 import 行 → `npm run generate:modules` → `npm run build-matrix`。组合根 + 自动生成消除了"忘了注册"类错误。
2. **三重验证门禁**（lint + build strict + test）+ 零 any + `noUncheckedIndexedAccess`，重构安全网厚实。本次评估实测 lint/build 双绿。
3. **双副本同步有 CI 把关**：`.claude/rules/` 与 `rule-templates.ts` 的 STRICT 内容一致性校验 + 版本 bump 硬门禁（2026-08-16/2026-08-20 定规），历史 drift 已清零。
4. **生产代码 TODO 极少**（全仓 11 处，扣除 helpers.ts 自身 5 处仅 6 处），半成品欠条密度低。

**弱点**：

- **W8（中，与 W3/W6 叠加）**：改动 ToolDispatcher 的 executeToolCall 或 GodotServer.close() 时风险高度集中——前者一个方法串联八道门/校验段，后者每加一个全局态必须记得补对称清理（历史上多次因清理遗漏致测试隔离泄漏，AGENTS.md 有记录）。
- **W9（低）**：rule-templates.ts 1136 行模板数据与 .claude/rules/ 双副本结构意味着改规则要动两处（虽有 CI 兜底，心智负担仍在）。

## 维度五：易测试性 —— 4.0 / 5.0

**优势**：

1. **测试密度健康**：473 测试文件对 263 源文件（1.8:1），单元/回归/集成/E2E 冒烟四层分类明确（`test/regression/`、`test/integration/`、`test/e2e-full-tool-verification.test.ts`）。
2. **覆盖率阈值 CI 强制且自我修正**：阈值按"实测超 4% 即上调"规则维护（vitest.config.ts 注释留痕 2026-08-21 上调记录），防止阈值滞后变成假安全。
3. **平台差异有豁免记录**：`game-bridge.ts` 因 Linux CI vitest mock 平台 bug 退出覆盖率（issue #15），豁免理由与本地补偿（Windows 23/23 用例）都写在配置注释里——豁免可追溯而非静默。
4. **测试隔离基建化**：`test/helpers/path-isolation.ts` + globalSetup（gdscript-check fixture 填充防 GD 类测试挂死）。

**弱点**：

- **W10（中）**：63/263 src 文件无任何测试 import 引用（近似口径，barrel 间接覆盖不保障直接回归）。多数是小文件/入口文件，但其中 **6 个 ≥400 行文件无直接测试**是真实缺口：

  | 行数 | 文件 |
  |---|---|
  | 887 | `src/core/function-profiler.ts` |
  | 647 | `src/resources.ts` |
  | 528 | `src/dashboard/ui.ts` |
  | 500 | `src/tools/profiler-ops.ts` |
  | 489 | `src/tools/translation-ops.ts` |
  | 448 | `src/tools/uid-ops.ts` |

- **W11（低）**：branches 阈值 51% 显著低于其他三维（76/79/77），vitest.config.ts 注释自认"实测值未取，保守不动"——分支覆盖是当前盲区，下轮应补实测并上调。

## 问题清单（按处置优先级）

| 编号 | 严重度 | 问题 | 建议处置 |
|---|---|---|---|
| W6 | 高 | ToolDispatcher 的 executeToolCall ~200 行多职责方法 + buildMiddleware ~168 行内联中间件工厂；gdscript-executor/script.ts 均超 1200 行 | 按已有 section 边界拆方法/文件（confirm_and_execute 分支与 audit middleware 优先）；不新增行为，纯移动 |
| W10 | 中 | 6 个 ≥400 行文件无直接测试引用（function-profiler 887 行最大） | 优先补 function-profiler.ts 与 profiler-ops.ts（同主题，可一起补） |
| W3+W8 | 中 | 26 个模块级 setter，close() 手动对称清理靠纪律 | 维持"禁止新增"门禁；每次触碰相关文件时顺手迁移一个到构造器注入（渐进清算，不做一次性大改——与 AGENTS 定规一致） |
| W5 | 中 | helpers.ts 废弃桶拖 14+ 版本，45 位点未迁移 | 要么排期兑现删除（每批迁 10 个 import 位点），要么正式改口为"长期保留的兼容层"并更新文件头注释 |
| W11 | 低 | branches 覆盖率 51% 无实测依据 | 跑一次 `npm run test:coverage` 取实测 branches 值，按 4% margin 规则上调 |
| W1/W2/W4/W7/W9 | 低 | 反向依赖 / 监控面耦合 / ui-anim 模板微重复 / 内联 HTML / 双副本心智负担 | 顺手修（W1 下沉 BLOCKED_PROPS）；其余记录在案不强求 |

## 值得保留的做法（其他项目可借鉴）

1. 用 eslint `no-restricted-imports` 把架构分层约束变成 CI 机械门禁，而不是 code review 口头约定。
2. 组合根 import 清单自动生成（generate-all-modules.mjs），注册零手工。
3. 覆盖率阈值带"超 4% 必上调"的自我修正条款并把上调依据写进配置注释。
4. 样板收敛时"统一流程 + 差异参数化"（ops-runner 的 errorMapper/trusted 注入点设计）。
5. 平台豁免必须留 issue 指针 + 本地补偿说明（game-bridge.ts 先例）。

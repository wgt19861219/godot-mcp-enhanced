### 任务① 交付明细

- `src/core/tool-errors.ts:91`：新增 `ToolDeadlineError`（code=`TOOL_DEADLINE_EXCEEDED`，category=`timeout`，retryable=true）。与既有 `TimeoutError` 的分工：后者是 handler 内部业务超时（Godot 进程 30s 等），前者是 dispatcher 层最后一道网。
- `src/core/progress.ts:106`：新增 `withToolDeadline`——心跳+deadline 双 timer 内聚一体（deadline 触发即 reject 并在 finally 停心跳，不再向已终结请求发 progress）；两 timer 均 unref；executor 内 `fn().then(...)` 挂链，late settle 无副作用且不产生 unhandled rejection（审查维度 1 逐行推理验证）。
- `src/core/ToolDispatcher.ts:63`（`getToolDeadlineMs`）+ `:297`（接线）：包整个 `executeToolCall`，超时就地转 `opsErrorResult`（error_code/retryable/error_category/trace_id），不冒泡到 executeMiddleware Phase 2（那里会转 `'Tool execution error: ...'` 裸文本）。
- env `GODOT_MCP_TOOL_DEADLINE_MS`：默认 3600000ms，`<=0` 禁用（退化为纯心跳=改动前行为）。默认值对齐 `src/tools/qa/spec.ts:185` 的 `run_timeout_s` `.max(3600)`——审查维度 2 逐项 grep 全部工具超时上限（qa 套件墙钟 600s / execute_gdscript 120s / editor test_run 290s / nav bake 110s / DAP 30s / android export 300s），确认无超过 1h 的合法调用。
- **诚实边界**（代码注释+CHANGELOG 均声明）：deadline 触发后底层 fn 仍在跑（JS 无法中止 Promise），late settle 结果被丢弃——与客户端 idle 杀同款"白花钱的取消"，差别是客户端拿到明确错误而非无限等待。
- **已知取舍**：deadline 超时后 `clearInflight` 执行时底层仍在跑，该 in-flight 记录被移除（挂起 1h 的调用本身已是异常场景，报丧价值有限；审查评估合理可接受）。

## 三、任务②评估正文：STARTUP_CLEANUP 维持默认 false（用户裁决项）

**结论：维持 `feature-flags.ts:17` 的 `default: false`，不改为默认开。**

论据（全部锚定当前代码，非历史文档转述）：

1. **全系统扫描的匹配宽度决定误杀风险**。`src/core/orphan-cleanup.ts:83-84,138-171`：第二层扫描（fullSystemScan）匹配"命令行含 projectDir 的 Godot，跳过 `--editor`"——它**无法区分**三种进程：MCP 崩溃残留的真孤儿 / 用户手动跑的同项目游戏（正在调试的会话）/ 另一个 MCP 实例正管的游戏。
2. **误杀场景真实存在且代价不对称**：① `MULTI_INSTANCE` 双 server 管同一项目时，后启动实例的启动清理会杀掉先启动实例正管的游戏（灾难性互杀）；② server 崩溃→重启的间隙用户手动开了游戏调试→被杀（丢失正在调试的会话）。误杀代价（用户丢失活动会话）> 孤儿残留代价（手动 taskkill 一条命令）。
3. **默认关是踩过坑后的有意设计，且历史文档表述已被后续修复改变**：2026-07-31 审查文档写"第二层全系统扫描需双 env opt-in"，该表述在 2026-08-07 修复（`src/GodotServer.ts:668-678`）后**已过时**——现状是单 flag（`GODOT_MCP_STARTUP_CLEANUP=true`）+ `projectPath` 双条件，开启即自动传 `fullSystemScan: true`（修复了原"单独开启是 no-op 的虚假安全感"）。修复让 flag 重新有效，但没有改变默认关的决策——因为第 1、2 条论据未变。
4. **收益侧已有兜底**：会话内 60s 周期 orphan 扫描（第一层，只遍历本会话 spawnedPids，安全）；崩溃场景有 in-flight 报丧（下个 server 启动 stderr 诊断可见，`src/core/inflight.ts:88-127`，探活防多实例误报）。
5. **后续建议（不实施，记入待办候选）**：doctor 诊断时检测疑似残留 Godot 进程并提示 opt-in 清理命令（诊断不动作，零误杀风险）——把 opt-in 的可达性问题用安全的方式缓解。

## 六、值得进 memory 的工程教训

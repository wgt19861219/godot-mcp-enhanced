## 批 2：W5 — helpers.ts 废弃桶退役（三步走）

**目标**：兑现拖了 14+ 小版本的清理承诺，消除"计划内清理不兑现"先例。粗估 1-1.5 天。

### Step 1 — 自有函数安家

helpers.ts 的自有函数按语义拆两个新家（不建"换个名字的桶"）：

| 函数 | 新家 | 理由 |
|---|---|---|
| `requireString` / `requireNumber` / `requireProjectPath` | `src/core/args-validation.ts`（新建） | 参数校验语义；core 层（ToolDispatcher）与 tools 层都在用，须放 core |
| `ensureDir` / `buildSafeEnv` | `src/core/fs-utils.ts`（新建，若与现有模块语义重叠则并入而非新建——落地时先 grep core/ 现有导出再定） | fs/env 工具语义 |
| `allowOutsideProjectPaths` | **直接删除** | 已 `@deprecated since v0.18.0`，注释指引用 `isPathInAllowedRoots()`；先 `grep -rn "allowOutsideProjectPaths" src/ test/` 确认调用方为零或逐个迁移 |

re-export 部分无需安家——三个 split 模块（path-utils / config-parser / file-scanner）本就是目标。

### Step 2 — 45 个 import 位点迁移

- **方式**：写一次性迁移脚本（node，放 `scripts/` 外的临时目录，用后删）：读取每个位点文件的 `import { ... } from '...helpers.js'` 行 → 按符号→目标模块映射表（path-utils 符号清单 + config-parser + file-scanner + args-validation + fs-utils）重写为 1-N 条直接 import → 输出 diff 供人工核对。
- **注意**：一个 import 行可能混多个来源（实测样本：`import { isPathInAllowedRoots, parseGodotConfig } from '../helpers.js'` 跨 path-utils/config-parser 两个目标）——脚本必须按符号拆行。
- **验收**：`grep -rln "helpers\.js" src --include="*.ts"` 零命中（helpers.ts 自身除外）；`npm run lint && npm run build && npm test` 全绿。
- **分批建议**：45 位点一次 PR 偏大，按目录分两个 commit（tools 域 33 个 / core+根+CLI+dashboard 12 个），同分支同批验收。

### Step 3 — 删除 src/helpers.ts + 更新注释

- 删文件；同步检查 `src/tools/shared.ts` 桶与 `.claude/rules/`、`rule-templates.ts` 是否提及 helpers.ts（grep 确认）；CHANGELOG `[Unreleased]` 记一条。
- **验收**：`grep -rn "from '\./helpers\.js'\|from '\.\./helpers\.js'" src test` 零命中；三重门禁全绿。

**风险与回滚**：纯 import 路径改写 + 函数搬家，行为零变化；单分支内按 commit 粒度可回滚。

## 批 3：W6 — ToolDispatcher 拆分（纯重构，行为零变化）

**目标**：把 executeToolCall（~200 行）与 buildMiddleware（~168 行）按既有 section 边界拆到可读粒度。粗估 1 天 + 审查。

**前提确认（已满足）**：3217 行既有 dispatcher 测试做安全网；本批**不改任何逻辑、不动签名语义**，测试文件**零改动**必须全绿——这是"纯移动"的机械判据。

### 3a. executeToolCall 拆三段

| 新私有方法 | 搬移内容（现行号） | 说明 |
|---|---|---|
| `_enforceGates(name, args)` | profile 硬隔离 + action-gate 前置拦截（317-341） | 返回 `opsErrorResult` 或 null；两道门的动态工具名反查逻辑原样搬 |
| `_handleConfirmAndExecute(...)` | confirm_and_execute 分支（400-477，约 78 行） | 含 MRTR 两轮 + `GODOT_MCP_ALLOW_UNSAFE_CONFIRM` 降级路径；内部已内聚调用 `_confirmExecute` + `_auditConfirmedExecution`，是最干净的切割线 |
| （可选）`_validateAndPrepareArgs(...)` | 0.5-1.5 段（默认 project_path 注入 / findGodot / 参数与 schema 校验 / ReadOnlyGuard / 路径白名单，346-398） | 若拆完前两段主方法已 ≤120 行则不做——**简约优先，不为一致性而拆** |

拆后 executeToolCall 主干应为：gates → 准备与校验 → confirm 分支 → 确认令牌检查 → `_dispatchEditorOrHeadless` → 统一 catch。

### 3b. buildMiddleware 拆 audit 工厂

- 把 audit middleware（593-673，约 80 行）抽为模块级工厂 `createAuditMiddleware()`（同文件下方或独立 `src/core/audit-middleware.ts`——按届时 ToolDispatcher.ts 行数定）。
- **⚠️ 顺序约定必须保住**：现有注释明确 audit 必须是"最后一个带 after 的 hook"（Nit-5，STRICT 改判依赖此序）。抽离后 `buildMiddleware` 里的注册顺序不变，并在工厂函数头注释搬运这条约定。
- healthSample / telemetry 两段各 ~40 行，留在原处即可（未达必须拆的阈值）。

### 验收与风险

- **验收**：`test/core/ToolDispatcher*.test.ts` 三文件 git diff 为零且全绿；`npm run lint && npm run build && npm test` 全绿；executeToolCall ≤ 150 行。
- **风险点**：① `currentMode`/`currentExecutor` 快照语义——注释（C-CONC-1）说明并发请求下禁止用实例字段传递，拆出的方法必须显式传参（`_handleConfirmAndExecute` 签名照抄 `_confirmExecute` 的传参模式即可）；② middleware 注册顺序（见上）；③ confirm 分支里 `srvCtx`/`clientTasksCapable`/`callerAgentId` 等长参数链照搬不省略。
- **显式不在本批**：`gdscript-executor.ts`（1579 行）与 `script.ts`（1236 行）的拆分——核心执行链、测试密度低于 dispatcher，待本批经验 + 批 4 补测后再评估（见"后续批"）。

## 全局流程要求（每批通用）

1. **分支**：每批独立 feature 分支（如 `refactor/w5-helpers-retire`），Conventional Commits（`refactor:`/`test:`/`chore:` 前缀）。
2. **门禁**：合并前 `npm run lint && npm run build && npm test` 三重全绿（AGENTS 完成前强制检查）；批 1a 额外跑 coverage。
3. **审查**：每批落地后派 `code-reviewer` 子 agent 独立审查，产出 `docs/reviews/YYYY-MM-DD-<批名>.md`（AGENTS §plan 落地后必出第三方审查文档）；批 3 审查必须专项核对"测试零改动 + 行为零变化"两条判据。
4. **memory**：每批完成登 memory（feature-decision-log + 教训）；批 3 若发现新的并发/顺序约束，同步更新本方案风险段。
5. **默认不发版**：全部走 CHANGELOG `[Unreleased]`，不 bump 版本（AGENTS 2026-08-19 定规）——除非触碰 `rule-templates.ts` / `.claude/rules/`（本方案预计不触碰）。

## 优先顺序论证

批 1 → 批 2 → 批 3 → 批 4：批 1 最小风险先验证流程；批 2 机械性高且独立；批 3 有厚测试保护放在 import 清理之后可使 diff 更干净（避免 45 位点迁移与 dispatcher 重构混在同屏 review）；批 4 纯增量无冲突可随时插入。批 2 与批 3、批 4 之间无硬依赖，人力充足时可并行推进。
